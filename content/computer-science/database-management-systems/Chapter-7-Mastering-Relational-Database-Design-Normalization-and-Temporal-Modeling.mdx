## Introduction

Did you know that simply decomposing a database table to eliminate duplicate data can actually _destroy_ your information if done incorrectly? While trying to clean up redundancy, you might inadvertently mix up critical connections between records—creating "phantom" data that never existed. Welcome to the mathematical foundation of relational database design, where we use functional and multivalued dependencies to systematically transform messy, redundant tables into precise, bulletproof schemas.

### Learning Objectives:

By completing this lesson, you will be able to:

- Determine if a decomposition is lossless or lossy using relational algebra.
- Compute the closure of attribute sets and find canonical covers for functional dependencies.
- Design schemas in Boyce-Codd Normal Form (BCNF), Third Normal Form (3NF), and Fourth Normal Form (4NF).
- Identify and mitigate database design flaws using atomic domains and naming strategies.
- Model complex temporal data with valid-time intervals and implement temporal primary and foreign keys.

## Features of Good Relational Designs

The ultimate goal of relational database design is to construct a set of relation schemas that store information without unnecessary redundancy, while enabling straightforward data retrieval.

Consider an combined schema `in_dep(ID, name, salary, dept_name, building, budget)`. While this schema eliminates the need for natural joins in some queries, it introduces several severe design flaws:

- **Redundancy & Inconsistency:** The department's building and budget are repeated for every single instructor in that department. If a budget is updated in one row but missed in another, the database becomes inconsistent.
- **Insertion Anomalies:** We cannot represent department information (like its budget or building) unless there is at least one instructor hired into that department, because `ID` cannot be null.
- **Deletion Anomalies:** If the last instructor in a department is deleted, all historical data regarding that department's budget and building is completely lost.

To resolve these anomalies, we must perform **decomposition**—splitting a relation schema into smaller schemas. However, decompositions can be highly problematic if they are **lossy**.

If we decompose `employee(ID, name, street, city, salary)` into `employee1(ID, name)` and `employee2(name, street, city, salary)`, and two employees share the same name (e.g., "Kim"), a natural join on `name` will produce a proper superset of the original relation. This introduces false records and loses the exact mapping of `ID` to address and salary.

Conversely, a decomposition of $R$ into $R_1$ and $R_2$ is **lossless** if, for all legal instances of relation $r(R)$: $$\Pi_{R_1}(r) \bowtie \Pi_{R_2}(r) = r$$ If the natural join produces a proper superset ($r \subset \Pi_{R_1}(r) \bowtie \Pi_{R_2}(r)$), the decomposition is lossy.

## Decomposition Using Functional Dependencies

To systematically verify if a design is in a desirable normal form, we must formalize real-world constraints using **functional dependencies (FDs)**. Let's establish our notation:

- Greek letters (e.g., $\alpha, \beta$) denote sets of attributes.
- Uppercase Roman letters (e.g., $R$) denote relation schemas.
- $r(R)$ represents a relation $r$ over schema $R$.
- $K$ represents a superkey for $R$.

An instance of $r(R)$ satisfies the functional dependency $\alpha \rightarrow \beta$ if, for all pairs of tuples $t_1$ and $t_2$ in $r$ where $t_1[\alpha] = t_2[\alpha]$, it must also be true that $t_1[\beta] = t_2[\beta]$.

An FD is **trivial** if it is satisfied by all possible relations. This occurs when the right-hand side is a subset of the left-hand side (i.e., $\beta \subseteq \alpha$). For example, $A \rightarrow A$ and $AB \rightarrow A$ are always trivial. We say that $K$ is a superkey for $r(R)$ if the FD $K \rightarrow R$ holds.

We can use functional dependencies to determine when a binary decomposition of $R$ into $R_1$ and $R_2$ is guaranteed to be lossless. The decomposition is lossless if at least one of the following FDs is in the closure $F^+$:

- $R_1 \cap R_2 \rightarrow R_1$
- $R_1 \cap R_2 \rightarrow R_2$

In plain terms, the attributes common to both schemas must form a superkey for at least one of the schemas. To guarantee consistency when a schema is decomposed, we must enforce that $R_1 \cap R_2$ is the primary key of $R_1$ and a foreign key in $R_2$ (or vice-versa).

## Normal Forms

We classify schemas into different **normal forms** based on the types of functional dependencies they satisfy.

### Boyce-Codd Normal Form (BCNF)

BCNF eliminates all redundancy discoverable by functional dependencies. A relation schema $R$ is in BCNF with respect to a set $F$ of FDs if, for all functional dependencies in $F^+$ of the form $\alpha \rightarrow \beta$ (where $\alpha \subseteq R$ and $\beta \subseteq R$), at least one of the following holds:

- $\alpha \rightarrow \beta$ is trivial (i.e., $\beta \subseteq \alpha$).
- $\alpha$ is a superkey for $R$.

If BCNF is violated by a non-trivial dependency $\alpha \rightarrow \beta$, we decompose $R$ into:

1. $(\alpha \cup \beta)$
2. $(R - (\beta - \alpha))$

While BCNF is highly desirable, it is not always **dependency-preserving**. Consider a schema `dept_advisor(s_ID, i_ID, dept_name)` with constraints:

- An instructor belongs to one department: `i_ID -> dept_name`
- A student has at most one advisor per department: `s_ID, dept_name -> i_ID`

This schema violates BCNF because `i_ID` is not a superkey. Decomposing it to BCNF yields `(s_ID, i_ID)` and `(i_ID, dept_name)`. However, the critical constraint `s_ID, dept_name -> i_ID` can no longer be checked within a single relation without computing a natural join. This design is not dependency-preserving.

### Third Normal Form (3NF)

To handle scenarios where BCNF cannot preserve dependencies, we relax the constraint slightly using 3NF. A relation schema $R$ is in 3NF with respect to $F$ if, for all FDs in $F^+$ of the form $\alpha \rightarrow \beta$, at least one of the following holds:

- $\alpha \rightarrow \beta$ is trivial.
- $\alpha$ is a superkey for $R$.
- Each attribute $A$ in $\beta - \alpha$ is contained in a candidate key for $R$.

In our `dept_advisor` example, because `dept_name` (which is $\beta - \alpha$ under `i_ID -> dept_name`) is part of the candidate key `(s_ID, dept_name)`, the relation is already in 3NF!

### Comparing BCNF and 3NF

With functional dependencies, database designers face a classic trilemma. It is always possible to achieve lossless decomposition and BCNF, _or_ lossless decomposition, 3NF, and dependency preservation. If we cannot get dependency-preserving BCNF, we must choose between accepting potential redundancy (3NF) or accepting expensive join operations to check constraints (BCNF). Note that standard SQL only natively enforces FDs where the left-hand side is a key, meaning that non-key FDs are incredibly difficult to maintain in practice without custom application code or materialized views.

## Functional-Dependency Theory

To systematically reason about dependencies and build algorithms for normalization, we must study **Functional-Dependency Theory**.

### Armstrong's Axioms

The closure of $F$ (denoted $F^+$) is the set of all functional dependencies logically implied by $F$. We calculate $F^+$ using **Armstrong's Axioms**, which are both **sound** (they generate only correct FDs) and **complete** (they generate all valid FDs):

- **Reflexivity:** If $\beta \subseteq \alpha$, then $\alpha \rightarrow \beta$.
- **Augmentation:** If $\alpha \rightarrow \beta$, then $\gamma\alpha \rightarrow \gamma\beta$ for any $\gamma$.
- **Transitivity:** If $\alpha \rightarrow \beta$ and $\beta \rightarrow \gamma$, then $\alpha \rightarrow \gamma$.

From these axioms, we can derive three additional highly useful rules:

- **Union:** If $\alpha \rightarrow \beta$ and $\alpha \rightarrow \gamma$, then $\alpha \rightarrow \beta\gamma$.
- **Decomposition:** If $\alpha \rightarrow \beta\gamma$, then $\alpha \rightarrow \beta$ and $\alpha \rightarrow \gamma$.
- **Pseudotransitivity:** If $\alpha \rightarrow \beta$ and $\gamma\beta \rightarrow \delta$, then $\alpha\gamma \rightarrow \delta$.

### Attribute Closure

Computing the full set $F^+$ is computationally expensive because a relation with $n$ attributes has $2^{2n}$ possible FDs. Instead, we compute the **attribute closure** of a specific set of attributes $\alpha$ (denoted $\alpha^+$) under $F$.

We initialize `result := α`. We then repeatedly scan our set of FDs: if we find an FD $\beta \rightarrow \gamma$ where $\beta \subseteq \text{result}$, we update `result := result ∪ γ`. We repeat this until `result` stops changing. This algorithm allows us to easily check if $\alpha$ is a superkey (by verifying if $\alpha^+ = R$) or if $\alpha \rightarrow \beta$ holds (by verifying if $\beta \subseteq \alpha^+$).

### Canonical Cover

A **canonical cover** $F_c$ is a simplified, minimal set of functional dependencies equivalent to $F$ (meaning $F_c^+ = F^+$). It must satisfy two rules:

1. No FD in $F_c$ contains an **extraneous attribute**.
2. Each left-hand side of an FD in $F_c$ is unique.

An attribute $A$ in $\alpha \rightarrow \beta$ is extraneous if:

- **On the left-hand side (**$A \in \alpha$**):** Removing $A$ from $\alpha$ results in a dependency $(\alpha - A) \rightarrow \beta$ that is still logically implied by $F$. To test this, check if $\beta \subseteq (\alpha - A)^+$ under $F$.
- **On the right-hand side (**$A \in \beta$**):** Removing $A$ results in a weaker dependency $\alpha \rightarrow (\beta - A)$ that, together with the rest of $F$, still logically implies $F$. To test this, check if $\alpha \rightarrow A$ can be inferred from $F' = (F - \{\alpha \rightarrow \beta\}) \cup \{\alpha \rightarrow (\beta - A)\}$.

### Testing Dependency Preservation

Let $R$ be decomposed into $R_1, R_2, \dots, R_n$. The **restriction** of $F$ to $R_i$ (denoted $F_i$) is the set of all FDs in $F^+$ that only use attributes in $R_i$. The decomposition preserves dependencies if $(F_1 \cup F_2 \cup \dots \cup F_n)^+ = F^+$.

Instead of computing $F^+$, we can test each FD $\alpha \rightarrow \beta$ in $F$ using a polynomial-time algorithm:

1. Set `result := α`.
2. For each $R_i$ in the decomposition, update `result := result ∪ (((result ∩ R_i)^+ ∩ R_i))`.
3. Repeat step 2 until `result` is stable. If $\beta \subseteq \text{result}$, the dependency $\alpha \rightarrow \beta$ is preserved.

## Algorithms for Decomposition Using Functional Dependencies

To design real-world relational databases, we rely on precise, algorithmic execution of BCNF and 3NF decompositions.

### BCNF Decomposition Algorithm

Given a schema $R$ and a set of FDs $F$:

1. Initialize `result := {R}`.
2. While there is a schema $R_i \in \text{result}$ that is not in BCNF:
   - Find a non-trivial FD $\alpha \rightarrow \beta$ holding on $R_i$ where $\alpha^+ \cap R_i \neq R_i$ and $\alpha \cap \beta = \emptyset$.
   - Decompose $R_i$ by replacing it in `result` with two new schemas: $(R_i - \beta)$ and $(\alpha \cup \beta)$.
3. Repeat until all schemas in `result` are in BCNF.

_Note on testing BCNF on a decomposed relation_ $R_i$_:_ We cannot simply use the FDs in $F$. We must test whether every subset $\alpha$ of $R_i$ satisfies: $\alpha^+$ either contains no attributes of $R_i - \alpha$, or includes all attributes of $R_i$. If this condition is violated, the FD $\alpha \rightarrow (\alpha^+ - \alpha) \cap R_i$ is a BCNF violation.

### 3NF Decomposition Algorithm (Synthesis Algorithm)

This algorithm synthesizes a set of 3NF, lossless, dependency-preserving schemas from a canonical cover $F_c$:

1. Initialize $i := 0$.
2. For each functional dependency $\alpha \rightarrow \beta$ in $F_c$:
   - Update $i := i + 1$.
   - Create a relation schema $R_i := \alpha \cup \beta$.
3. If none of the generated schemas $R_j$ contains a candidate key for the original schema $R$:
   - Update $i := i + 1$.
   - Create a new schema $R_i$ containing any candidate key of $R$.
4. Optionally, remove redundant schemas: if any $R_j$ is a proper subset of another schema $R_k$, delete $R_j$.
5. Return the collection of schemas.

## Decomposition Using Multivalued Dependencies

Even BCNF schemas can suffer from severe redundancy if they contain independent, multi-valued properties of an entity. Consider a schema `inst(ID, dept_name, street, city)` where an instructor can belong to multiple departments and have multiple addresses.

Since no functional dependencies hold on this schema, it is technically in BCNF. However, if instructor `22222` has 2 departments and 2 addresses, we are forced to record 4 tuples to ensure that every department is matched with every address. To formalize and eliminate this issue, we define **multivalued dependencies (MVDs)**.

### Multivalued Dependencies

Let $r(R)$ be a relation schema, with $\alpha \subseteq R$ and $\beta \subseteq R$. The MVD $\alpha \rightarrow\rightarrow \beta$ holds on $R$ if, for all pairs of tuples $t_1$ and $t_2$ in any legal instance of $r$ where $t_1[\alpha] = t_2[\alpha]$, there exist tuples $t_3$ and $t_4$ in $r$ such that:

- $t_3[\alpha] = t_4[\alpha] = t_1[\alpha]$
- $t_3[\beta] = t_1[\beta]$ and $t_3[R - \beta] = t_2[R - \beta]$
- $t_4[\beta] = t_2[\beta]$ and $t_4[R - \beta] = t_1[R - \beta]$

Essentially, an MVD states that the values for $\beta$ and $R$ $- \beta$ are completely independent for a given $\alpha$.

- An MVD is **trivial** if $\beta \subseteq \alpha$ or $\beta \cup \alpha = R$.
- Every functional dependency is also a multivalued dependency (if $\alpha \rightarrow \beta$, then $\alpha \rightarrow\rightarrow \beta$).
- MVDs satisfy the **complementation rule**: if $\alpha \rightarrow\rightarrow \beta$ holds, then $\alpha \rightarrow\rightarrow R - \alpha - \beta$ also holds.

### Fourth Normal Form (4NF)

We use MVDs to define **Fourth Normal Form (4NF)**, which is strictly stronger than BCNF. A relation schema $R$ is in 4NF with respect to a set $D$ of functional and multivalued dependencies if, for all MVDs in $D^+$ of the form $\alpha \rightarrow\rightarrow \beta$ (where $\alpha, \beta \subseteq R$), at least one of the following holds:

- $\alpha \rightarrow\rightarrow \beta$ is trivial.
- $\alpha$ is a superkey for $R$.

### 4NF Decomposition

The 4NF decomposition algorithm is identical to BCNF decomposition, but it operates on MVDs. If an MVD $\alpha \rightarrow\rightarrow \beta$ violates 4NF on schema $R_i$, we replace $R_i$ with $(R_i - \beta)$ and $(\alpha \cup \beta)$. This decomposition is guaranteed to be lossless because a decomposition into $R_1$ and $R_2$ is lossless if and only if $R_1 \cap R_2 \rightarrow\rightarrow R_1$ (or $R_2$).

## More Normal Forms, Atomic Domains, and First Normal Form

There are several additional normal forms that address even more subtle forms of redundancy:

- **Project-Join Normal Form (PJNF / 5NF):** Uses join dependencies to generalize MVDs.
- **Domain-Key Normal Form (DKNF):** The theoretical ultimate normal form, where all constraints are logical consequences of domain constraints and key constraints. PJNF and DKNF are rarely used in practice due to the lack of algorithmic rules.
- **Second Normal Form (2NF):** Of historical interest only, 2NF requires that no non-prime attribute is partially dependent on any candidate key. Every 3NF schema is automatically in 2NF.

### Atomic Domains and First Normal Form (1NF)

In the relational model, we require that all attribute domains are **atomic**—meaning their values are considered indivisible units.

A relation schema $R$ is in **First Normal Form (1NF)** if the domains of all attributes of $R$ are atomic. Examples of non-atomic values include:

- **Set-valued attributes:** Storing a set of phone numbers `{512-555-1234, 512-555-4321}` in a single column.
- **Composite attributes:** Storing a complex `address` object with subparts like street, city, and zip code in a single column instead of separating them.
- **Encoded identifiers:** An ID like `CS001` (where `CS` represents Computer Science and `001` is a sequence number). If your application programs have to split this string to extract the department name, the domain is non-atomic and violates 1NF.

While some modern database systems relax 1NF to support nested relations, JSON, or XML for specialized developer convenience, doing so can compromise data consistency and make declarative querying significantly more complex.

## Database-Design Process

Normalization must be contextualized within the broader database design lifecycle. There are several ways schemas are created:

1. Converting an Entity-Relationship (E-R) diagram to tables.
2. Ad hoc schema creation.
3. The **universal-relation approach** (starting with one massive relation containing all attributes and decomposing it).

If an E-R diagram is built carefully—properly identifying entities, relationships, and multivalued attributes—the generated tables will almost always be in 4NF. Normalization acts as a formal verification step to correct mistakes in the E-R design.

### Naming Conventions

Good design relies on the **unique-role assumption**: each attribute name must have a unique meaning in the database. Using the name `number` to mean phone number in one table and room number in another is a major design risk. Conversely, attributes with identical meanings across tables (like `dept_name`) should share the same name to make joins intuitive.

### Denormalization for Performance

Occasionally, database administrators deliberately introduce redundancy (called **denormalization**) to speed up queries that require expensive joins. However, this forces the application program to maintain consistency across copies of the data. A superior alternative supported by modern database engines is using a normalized schema combined with **materialized views**, shifting the maintenance burden from the developer to the database system.

## Modeling Temporal Data

Most databases store a snapshot of the real world at the current point in time. However, many systems require **temporal data**—data that has an associated time interval during which it is valid.

To represent temporal data, we add valid-time interval attributes, typically denoted as `start` and `end`. By convention (and standard SQL:2011), these intervals are closed on the left and open on the right: `[start, end)`. This prevents overlapping when one state transitions directly into the next.

### Temporal Functional Dependencies and Keys

When tracking historical data, traditional FDs like `course_id -> title` no longer hold, because a course's title can change over time. Instead, we define a **temporal functional dependency**: $$\alpha \xrightarrow{\tau} \beta$$ This states that $\alpha \rightarrow \beta$ holds on any temporary snapshot of the relation at any given point in time $t$.

Similarly, a traditional primary key constraint is insufficient because multiple records can share the same `course_id` (representing different valid time intervals). A **temporal primary key** requires that if two tuples have the same primary key attributes, their valid-time intervals must not overlap.

### Temporal Foreign Keys

A **temporal foreign key** ensures that for each tuple in the referencing relation with interval `[l, u)`, there is a matching set of tuples in the referenced relation whose combined, overlapping valid-time intervals completely cover `[l, u)`.

### SQL Implementation and PostgreSQL Workaround

SQL:2011 introduces native temporal declarations:

- Declaring an interval period: `period for validtime (start, end)`
- Declaring a temporal primary key: `primary key (course_id, validtime without overlaps)`

Because many database engines lack native temporal foreign/primary key support, systems like PostgreSQL allow workarounds using **exclude constraints** on range types (`tsrange`):

```
ALTER TABLE course
ADD CONSTRAINT course_no_overlap
EXCLUDE (course_id WITH =, validtime WITH &&);
```

This constraint uses the `=` operator to check for matching IDs and the `&&` operator to block overlapping ranges, robustly enforcing temporal database integrity.

## Summary

We have covered the rigorous mathematical theory and practical considerations of relational database design:

- **The Redundancy Problem:** Poor designs suffer from insertion, deletion, and update anomalies. Decomposition splits relations to solve this, but we must guarantee that splits are lossless.
- **Functional Dependencies:** $\alpha \rightarrow \beta$ forms the basis for normalization theory. We use Armstrong's Axioms (Reflexivity, Augmentation, Transitivity) to compute the dependency closure $F^+$.
- **Normal Forms:** BCNF eliminates all dependency-related redundancy but can sacrifice dependency preservation. 3NF guarantees dependency preservation but allows minor redundancy. 4NF introduces Multivalued Dependencies ($\alpha \rightarrow\rightarrow \beta$) to eliminate multi-attribute redundancies.
- **Algorithmic Design:** We can systematically synthesize 3NF schemas using canonical covers ($F_c$), ensuring no extraneous attributes exist.
- **Temporal Data:** Modeling history requires representing valid-time intervals `[start, end)` and enforcing complex non-overlapping constraints using temporal primary/foreign keys.
