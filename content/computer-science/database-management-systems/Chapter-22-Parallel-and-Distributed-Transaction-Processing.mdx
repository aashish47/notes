## Introduction

How do modern database systems process petabytes of data in seconds when a single CPU core would take days to complete the task? The secret lies in parallel and distributed query processing—orchestrating hundreds or thousands of processing cores to work in unison. In this lesson, we will explore the core algorithms, architectures, and optimization strategies that make large-scale, high-speed data processing possible.

### Learning Objectives:

- Contrast interquery and intraquery parallelism, as well as intraoperation and interoperation parallelism.
- Compare parallel sorting and join strategies, including range partitioning, external sort-merge, partitioned joins, and fragment-and-replicate joins.
- Explain the Exchange Operator model and how it encapsulates parallel execution.
- Understand how query engines adapt to shared-memory architectures, streaming data, and distributed heterogeneous data sources.

## Parallel Query Processing Overview

Parallel processing in database systems can be exploited in two distinct ways:

- **Interquery Parallelism:** The execution of multiple different queries in parallel across multiple nodes. This is the primary mechanism used to scale up Transaction Processing Systems (OLTP) to support a massive throughput of transactions per second. However, it does not speed up any individual transaction.
- **Intraquery Parallelism:** The processing of different parts of a single query in parallel across multiple nodes. This is essential for speeding up long-running, complex queries in Decision Support Systems (OLAP).

Within intraquery parallelism, we can further distinguish two styles:

- **Intraoperation Parallelism:** Parallelizing a single relational operation (e.g., sorting, join, or aggregation) across multiple nodes. Because the number of tuples in a relation is typically vast, the potential degree of intraoperation parallelism is extremely high.
- **Interoperation Parallelism:** Running different operations of a query tree in parallel. This can happen through **independent parallelism** (executing independent subtrees concurrently) or **pipelined parallelism** (streaming the output of one operator directly into another on separate nodes).

To study these concepts, we assume a baseline **shared-nothing architecture** with $n$ nodes ($N_1, N_2, \dots, N_n$). In this setup, each node has its own local processor, memory, and disk. Nodes communicate solely by exchanging messages over a network. This model is highly scalable and can easily simulate shared-memory or shared-disk systems.

## Parallel Sorting Algorithms

Sorting is a fundamental operation in database systems, often acting as a prerequisite for joins, duplicate elimination, and user-requested ordering. There are two primary techniques for parallel sorting:

**Range-Partitioning Sort** This algorithm operates in two steps:

1. **Redistribute:** The relation is partitioned using a range-partitioning strategy. For example, if we are sorting alphabetically, Node 1 receives tuples starting with A–G, Node 2 receives H–P, and Node 3 receives Q–Z. Each node reads its local data, determines the destination node for each tuple, and transmits it over the network. Each node then writes its received partition to local disk.
2. **Local Sort:** Each node sorts its local partition independently using a standard sequential sorting algorithm (data parallelism).

The final result is obtained by simply concatenating the sorted partitions from the nodes in order. To prevent load imbalances, a balanced range-partition vector must be chosen. Techniques like virtual node partitioning—mapping multiple virtual nodes to physical nodes in a round-robin fashion—help mitigate data skew.

**Parallel External Sort-Merge** As an alternative that does not require pre-computing balanced ranges, parallel external sort-merge works as follows:

1. **Local Sort:** Each node $N_i$ sorts the data currently residing on its local disk to produce local sorted runs.
2. **Range Partition and Merge:** The system range-partitions these pre-sorted runs across the nodes. Crucially, the sorted streams are sent in blocks to avoid network overhead. Each node $N_i$ performs an ordered merge on the incoming pre-sorted streams to produce a single, locally sorted run. Concatenating these runs yields the final sorted relation.

## Parallel Joins

Parallel join algorithms partition input relations over multiple nodes so that each node can compute a subset of the join locally.

**Partitioned Join** For equi-joins (e.g., $r \bowtie_{r.A = s.B} s$), we can partition both relations across $m$ nodes using the exact same partitioning function on the join attributes. This function can be range-partitioning or hash-partitioning.

Once partitioned, each node $N_i$ performs a local join of its partitions $r_i$ and $s_i$. Depending on the local join technique chosen, this results in:

- **Partitioned Parallel Hash Join:** Node $N_i$ further hashes the incoming partitions $r_i$ and $s_i$ into local memory-sized buckets using a secondary hash function $h_1$ (distinct from the network partitioning hash function $h_0$).
- **Partitioned Parallel Merge Join:** Local partitions $r_i$ and $s_i$ are sorted and merged locally.
- **Partitioned Parallel Nested-Loop Join:** Nodes perform nested-loop joins on local partitions.

**Fragment-and-Replicate Join** When dealing with non-equi-joins (e.g., inequality conditions like $r \bowtie_{r.A < s.B} s$ partitioned joins cannot be used. Instead, we use fragment-and-replicate:

- **Asymmetric Fragment-and-Replicate (Broadcast Join):** Relation $r$ is partitioned across all nodes (using any scheme, like round-robin). The other relation, $s$, is replicated (broadcast) to every single node. Each node $N_i$ then computes the join of its local fragment $r_i$ with the complete relation $s$. This is highly effective even for equi-joins if $s$ is very small.
- **Symmetric Fragment-and-Replicate:** Relation $r$ is partitioned into $n$ pieces, and $s$ is partitioned into $m$ pieces. The system arranges at least $n \times m$ nodes in a grid. Fragment $r_i$ is replicated to all nodes in row $i$, and fragment $s_j$ is replicated to all nodes in column $j$. Node $N_{i,j}$ then computes $r_i \bowtie s_j$.

**Handling Skew in Parallel Joins** Data skew (where some partition values occur far more frequently than others) can lead to a single node being heavily overloaded, delaying the entire query. This is mitigated via:

- **Skew Avoidance:** Utilizing virtual-node partitioning to distribute highly skewed data across multiple real nodes.
- **Dynamic Skew Handling (Work Stealing):** The system monitors progress. If a node finishes its assigned virtual nodes and becomes idle, it dynamically 'steals' a virtual node task from a busy node's queue, pulling the necessary data over the network to process it.

## Other Relational Operations and MapReduce

Beyond sorting and joins, database engines parallelize other relational operators:

- **Selection (**$\sigma_\theta(r)$**):** If the selection attribute is the partitioning attribute, the query is routed only to the matching node(s). Otherwise, the selection runs in parallel across all nodes.
- **Duplicate Elimination:** This can be parallelized by partitioning tuples via hashing or range partitioning, then running duplicate elimination locally at each node.
- **Aggregation:** The relation is partitioned on the grouping attributes, and aggregation is performed locally. To reduce network transfer cost, **partial aggregation** is used: each node computes local partial aggregates (e.g., local sums and counts), sends only these partial results over the network, and a final aggregation step sums up the partials.

**Map and Reduce Operations** The MapReduce framework is closely related to parallel database operations:

- **Map:** A user-defined function invoked on individual input records, emitting intermediate `(key, value)` pairs. It behaves like a generalized projection.
- **Shuffle/Repartition:** The system automatically groups all values associated with the same intermediate key, partitioning them across workers using range or hash partitioning.
- **Reduce:** A user-defined function invoked per intermediate key, iterating over its collection of values to compute aggregates. It behaves like a user-defined aggregation operator.

MapReduce systems achieve extreme scale by executing map and reduce tasks across thousands of workers, using distributed filesystems like the Hadoop File System (HDFS) to ensure data is colocated with computation.

## Parallel Evaluation of Query Plans

To execute a complex query plan containing multiple operations, the query engine combines intraoperator and interoperator parallelism.

### Interoperation Parallelism

- **Pipelined Parallelism:** Output tuples of operator $A$ are consumed by operator $B$ on a separate node before $A$ finishes. Database engines prefer a **producer-driven (push) model** for pipelined parallel execution. In this model, producers push batches of tuples into a buffer, allowing both producer and consumer to execute concurrently.
- **Independent Parallelism:** Subtrees of a query plan that do not depend on one another (such as two different joins) are scheduled to execute simultaneously on different nodes.

**The Exchange Operator Model** Developed in the Volcano parallel database, the exchange-operator model is a powerful abstraction that encapsulates all parallel communication.

Instead of rewriting standard relational operators (like joins or sorts) to be parallel-aware, the system inserts an **Exchange Operator** into the query tree. This operator handles:

1. **Partitioni\*\***ng (at source nodes):\*\* Splitting data using hash, range, or broadcast (replicating) strategies.
2. **Merging (at destination nodes):** Collecting incoming data via **random merge** (preserving no order) or **ordered merge** (maintaining pre-sorted order).

This architecture allows the local relational operators to remain entirely unaware of parallelism, pulling data locally while the exchange operator transparently routes tuples across the network.

**Fault Tolerance in Query Plans** At a scale of thousands of nodes, node failures during a query are common.

- **MapReduce Fault Tolerance:** Map tasks write intermediate outputs to local disks. If a node fails, only its map task is re-run on another node. Reduce tasks only begin processing once all map inputs are fully materialized and fetched. This materialization step prevents the need to restart the entire query, but it disables pipelining.
- **Apache Spark (RDDs):** Spark uses Resilient Distributed Datasets (RDDs). It tracks the lineage of operations used to construct an RDD, allowing the system to recompute only the lost partitions of data on failure rather than the entire dataset.

## Query Processing on Shared-Memory Architectures

Modern parallel database nodes typically feature multiple multi-core processors sharing a single physical address space. Rather than running separate processes, these systems leverage lightweight **threads** and can optimize query processing in several ways:

- **Shared Memory Joins:** In an asymmetric broadcast join, the smaller relation does not need to be replicated over a network. Instead, a single copy is built in the shared memory, accessed concurrently by all threads.
- **Morsel-Driven Parallelism:** To eliminate skew, the probe relation is divided into tiny, memory-resident chunks called "morsels." Threads dynamically grab a morsel, process it against a shared hash table, and then grab another. This is an efficient form of in-memory work stealing.
- **Lock-Free Structures:** Constructing shared hash indexes in parallel can introduce heavy locking overhead. High-performance systems use lock-free data structures to allow multiple threads to build the shared index concurrently.

**NUMA (Non-Uniform Memory Access) Awareness** In modern multi-socket systems, memory is divided into physical banks linked directly to specific processor sockets. Accessing local memory is significantly faster than accessing remote memory banks. Database engines must be NUMA-aware, ensuring that a thread is scheduled on the processor core closest to the physical memory storing its target data.

**SIMD and GPU Acceleration** To process data even faster, query engines exploit **Single Instruction Multiple Data (SIMD)** instructions present in modern CPUs, which apply a single operation to an array of data points simultaneously. Similarly, Graphics Processing Units (GPUs) are increasingly leveraged to run highly parallel relational operations over arrays of data.

### Query Optimization for Parallel Execution

Parallel query optimizers must navigate a much larger plan space than sequential optimizers. They have to decide:

1. Which algorithm to use for each operator.
2. How to partition inputs and intermediate results (by which attributes and partitioning schemes).
3. How many nodes to allocate to each operation.
4. Which operators to pipeline, materialize, or execute independently.

### Cost Models

- **Resource Consumption Model:** Estimates the total sum of CPU, I/O, and network costs. It is simple to compute but does not guarantee the fastest query completion time.
- **Response-Time Cost Model:** Attempts to minimize the elapsed time of the query. It calculates costs as $\max(\text{CPU cost}, \text{I/O cost})$ for parallel processes, factoring in startup costs and skew. Estimating the execution time of the slowest node is highly data-dependent and complex.

**Data Colocation** To avoid expensive network shuffles during joins, systems use colocation. If two tables (e.g., `student` and `takes`) are partitioned on the exact same attribute (`ID`), rows with matching keys are guaranteed to reside on the same physical node. The query engine can then execute joins locally on each node without any network data exchange.

**Parallel Materialized View Maintenance** When a materialized view is distributed across multiple nodes, keeping it updated can be expensive. By parallelizing view maintenance using the Exchange Operator model, updates are routed to the specific nodes holding the affected partitions. Local view maintenance techniques are then applied to update the materialized results using only locally stored partition data.

## Parallel Processing of Streaming Data

Many modern applications require real-time analytics on high-velocity data streams (e.g., network monitoring or financial tickers). Many organizations deploy a **Lambda Architecture**, which forks incoming data streams into two copies: one sent to cold storage for batch analysis, and another sent to a stream processing system for real-time analysis.

**Routing of Tuples** Stream processing systems route continuous streams of tuples through a Directed Acyclic Graph (DAG) of operators.

- **Apache Storm:** Configures this routing graph statically as a "topology" of source nodes (spouts) and operator nodes (bolts).
- **Publish-Subscribe (e.g., Apache Kafka):** Operators subscribe to specific "topics" and publish outputs to other topics. Kafka partitions topics into "topic-partitions" with partition keys, ensuring that all tuples with the same key go to the same partition, which is then processed by a specific consumer thread.

**Stream Operations and State** Windowing divides continuous data streams into finite chunks based on time or tuple count. If an operator needs to compute rolling aggregations, it must maintain **state** (e.g., stored tuples or running totals). This state can be stored locally on the node for low latency, or written to a distributed storage system for safety.

**Fault Tolerance Semantics** Streaming systems must provide strict delivery guarantees during failures:

- **At-least-once:** Ensures no tuple is lost, but duplicates may be processed during recovery.
- **At-most-once:** Guarantees no duplicates, but tuples may be dropped on failure.
- **Exactly-once:** Guarantees each tuple is processed exactly once. This requires tracking offsets, periodic checkpointing of state to distributed filesystems, and deduplication of outputs using primary and hot-spare operator replicas.

## Distributed Query Processing

Distributed query processing deals with executing queries across multiple independent databases, which may be geographically dispersed or heterogeneous.

### Data Integration Approaches

- **Federated Database System:** Creates a unified global schema on top of local schemas. It maps queries on the global schema into local queries. Systems that only support queries but not updates are called **mediators**.
- **Data Virtualization:** Provides application access to multiple sources without enforcing a single global schema.
- **External Data (SQL MED):** Allows a database to query external tables (foreign tables) stored in other systems as if they were local tables.
- **Data Lake:** Stores data in various raw formats across multiple filesystems and databases, allowing them to be queried from a single interface.

### Schema Integration Mappings

- **Global-As-View (GAV):** The global schema is defined as a view over the local databases. It makes translating global queries into local queries very easy.
- **Local-As-View (LAV):** Local databases are defined as views over a conceptual global schema. This simplifies the process of identifying which specific nodes hold relevant data, allowing the optimizer to bypass irrelevant sites.

**The Semijoin Join Strategy** When joining relation $r_1$ (at Site 1) and $r_2$ (at Site 2), shipping all of $r_2$ over a slow network is highly inefficient if most tuples of $r_2$ do not match $r_1$. The semijoin strategy mitigates this:

1. Project the join attributes of $r_1$: $\Pi_{R_1 \cap R_2}(r_1)$.
2. Ship this projection to Site 2.
3. Join it with $r_2$ to filter out unmatched tuples: $temp \leftarrow r_2 \bowtie \Pi_{R_1 \cap R_2}(r_1)$.
4. Ship only this filtered subset ($temp$) back to Site 1 to complete the final join.

To minimize the network footprint of shipping the projection in step 1, systems use a **Bloom Filter**—a compact, probabilistic bitmap representing the join keys. A Bloom filter can result in some false positives (tuples shipped that do not actually join), but it will never have false negatives, ensuring absolute correctness of the final join result.

## Summary

### Key Takeaways:

- **Parallelism Types:** Intraquery parallelism is key for analytic query speedups. It relies heavily on intraoperation parallelism (e.g., parallel sorting, partitioned joins).
- **Sorting and Joins:** Parallel sorting uses range partitioning or external sort-merge. Parallel joins use partitioned hash/merge joins for equi-joins, and fragment-and-replicate (broadcast) joins for non-equi joins.
- **The Exchange Operator Model:** This model encapsulates parallel routing (partitioning and merging), allowing local database engines to operate unmodified.
- **Shared-Memory Optimizations:** Systems leverage multi-threading, lock-free indexes, morsel-driven processing to prevent skew, and NUMA-aware scheduling.
- **Stream Processing:** Relies on pub-sub systems like Kafka, state checkpointing, and deduplication to offer exactly-once processing semantics.
- **Distributed Querying:** Connects heterogeneous databases via GAV/LAV schema integration and uses semijoin filters (with Bloom filters) to minimize wide-area network data transfer costs.
